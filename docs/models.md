# Models

Hanoi Signal compares five ways to estimate typical mobile download speed. Each model predicts speed in Mbps from a location or its features; the application combines predictions around the selected point into a regional estimate. The data combines mobile networks and operators and does not represent a live speed test.

The production training input is `data/processed/hanoi_tiles.csv`: one row per Ookla tile, pooled over the latest four available quarters. A tile's download target is the test-weighted mean in log space, converted back to Mbps. Tower, cell, activity and geographic context features are generated by the same feature code used at prediction time. See the [data contract](data_contract.md) for the columns and [training guide](training.md) for the full procedure.

## Baseline models

### K-nearest neighbours (`knn`)

KNN uses latitude and longitude only. It finds the ten nearest distinct training locations using haversine distance and returns the equally weighted mean of their recorded download speeds. When training contains repeated coordinates, their targets are combined first using their supplied weights; the regional workflow uses the number of tests.

This is a geographic baseline: nearby observations influence a prediction, but the model does not directly use towers, land cover or network activity. Its estimates depend on where tests were collected, especially in sparsely sampled areas.

### Random Forest (`random_forest`)

Random Forest predicts from the shared location, tower, cell, activity and context features, excluding the physics-derived `theory_mbps` feature. The default model has 300 trees, a minimum of five samples per leaf and a fixed random seed. Training weights are the square root of the number of tests.

Missing optional context values are filled using medians learned from the training partition; entirely empty columns are filled with zero. The fitted imputer is saved with the forest. Required non-context inputs must be present and finite. This model provides a non-physics comparison for the hybrid.

## Physics and XGBoost models

The full comparison adds these three candidates. The physics estimate uses the project's 3GPP-based propagation and link-budget calculations with configured typical tower assumptions; actual operator power, frequency and bandwidth are not known. It is an approximation rather than a measured tower speed.

### Hybrid (`hybrid`)

The hybrid uses all configured model features, including `theory_mbps`. It starts with the physics estimate and uses XGBoost to learn a correction: the difference between `log1p` of measured speed and `log1p` of the theoretical speed. At prediction time the correction is added in log space and converted back to Mbps. The theoretical feature must be finite and non-negative.

### Physics only (`physics_only`)

This comparison returns the theoretical speed directly, without fitting a correction to measured speeds. It shows how the configured physics assumptions perform on their own.

### XGBoost only (`xgboost_only`)

This comparison trains XGBoost on the non-physics features and `log1p` of the measured download speed, then converts predictions back to Mbps. Comparing it with the hybrid helps assess whether adding the physics estimate improves this particular evaluation. Both XGBoost models default to 600 estimators, maximum depth 6, learning rate 0.03 and a fixed seed.

## Training, selection and serving

The baseline command compares KNN and Random Forest. After preparing the data and installing the editable package, run:

```sh
python -m speedmap.cli.train_baselines
```

For all five models, install the model requirements, rebuild physics-enabled features, and run the full comparison:

```sh
python -m pip install -r requirements-model.txt
python -m speedmap.cli.run_pipeline --step features --include-physics
python -m speedmap.cli.run_pipeline --step hybrid
```

Both workflows use five spatial `GroupKFold` splits grouped by 2 km blocks. Each tile receives a prediction from a model that did not train on that tile's block. Candidates are ranked by regional mean absolute error; ties use quality-level accuracy, then model name. The candidates are fitted on all available pooled tiles and saved together, with the winner as the default. These out-of-fold scores are used for model selection, not an independent final holdout. The [training guide](training.md) covers the inputs, metrics, saved reports and evaluation limitations.

Models and metadata are stored in `artifacts/models/regional/<run>/`, with a `LATEST` pointer in the parent directory. In model mode, the API loads the selected run and its available candidates. The web model picker or the optional `model` parameter to `/api/predict` can choose a candidate for a request; otherwise the saved winner is used. Older bundles may contain only one model. Keep the matching processed data and reference files with the artifact: input fingerprints and feature contracts are checked on loading. See the [API contract](api_contract.md) and [run guide](running_web_ui.md).

Standalone tile-quarter CV and training scripts are also available for each of the five models (`speedmap.cli.train_knn`, `train_random_forest`, `train_xgboost_only`, `train_hybrid`, and `train_physics_only`). Each evaluates five spatial `GroupKFold` splits on `data/processed/hanoi_train.csv`, writes `artifacts/reports/cv_<model>.csv`, and saves an all-row model under `artifacts/models/<model>/<run>/` with a `LATEST` pointer; the Web UI still serves the `regional` bundle. Trained models under `artifacts/models/`, evaluation reports under `artifacts/reports/regional/` and `artifacts/reports/cv_*.csv`, and the four matching interim/processed CSVs are tracked in Git.

## Uncertainty and limitations

The hybrid evaluation also measures tile-level split-conformal intervals using a separate calibration split. Their reported coverage and width concern held-out tiles; they do not establish coverage for regional estimates and are not returned as regional uncertainty intervals by the app.

The models estimate typical performance in the available historical data. They cannot distinguish operators, predict live congestion or guarantee service at a point. Sparse observations and estimated tower positions limit accuracy; the app may add grid predictions in areas with few observed tiles, and those extra samples are not directly validated by the regional evaluation. See [interpretation and limits](training.md#interpretation-and-limits).

The separate TensorFlow Group Task 2 exercise (`speedmap.cli.group_task_model`) trains on tile-quarter data and writes its own metrics and figure. It does not create the regional bundle or serve predictions in the web application.
